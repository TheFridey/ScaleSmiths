5. ASCEND machine-route security audit
Conduct a comprehensive manual security review of:

```
/api/ascend/worker
/api/ascend/v1/capabilities
/api/ascend/v1/operations
/api/ascend/v1/operations/[id]
/api/ascend/v1/operations/[id]/cancel
/api/expansion/automation/engine
```

Inspect the complete implementation, including middleware, service identity management, execution engine, database constraints, worker driver and action handlers.
Specifically investigate the following potential weaknesses. These are investigation targets, not confirmed vulnerabilities:
Service identity isolation

* Whether worker claims correctly enforce allowed action types.
* Whether execution start revalidates identity capabilities.
* Whether lease renewal verifies the owning service identity.
* Whether a different authenticated worker can renew or manipulate another worker's lease.
* Whether revoked identities can retain effective execution privileges.
* Whether token rotation immediately invalidates old credentials.
* Whether identity scope is enforced consistently across all routes.

Idempotency and scope

* Whether idempotency comparisons include execution scope.
* Whether payload fingerprints bind all security-relevant execution parameters.
* Whether identical payloads across different markets can collide.
* Whether conflicting requests correctly return a conflict response.
* Whether concurrent submissions can bypass cooldown or rate restrictions.

Market and data isolation

* Whether action handlers correctly respect their declared market scope.
* Whether aggregate queries accidentally expose cross-market information.
* Whether execution status endpoints expose records belonging to unrelated identities.
* Whether founder-only diagnostics are appropriately restricted.

Worker safety

* Lease ownership and expiry.
* Duplicate execution prevention.
* Stale worker recovery.
* Concurrency enforcement.
* Cancellation races.
* Emergency-stop races.
* Database statement timeouts.
* Cooperative versus enforceable execution deadlines.
* Recovery after database disconnection.
* Malformed or oversized requests.
* Replay resistance.

Action classification
Verify that every action advertised as read-only is actually read-only with respect to business records.
Pay particular attention to `review.queue_preparation`, which may create internal review records.
Do not classify internal mutation as read-only merely because it does not send communications or alter financial records.
Implement fixes and regression tests for every confirmed defect.

7. Supervised first execution
Prepare and verify the first controlled production ASCEND operation.
Use `ops.queue_health` as the initial candidate, subject to verification that it performs only aggregate reads and permitted execution bookkeeping.
Requirements:

1. Confirm global emergency stop remains engaged initially.
2. Confirm every automation is disabled.
3. Create a narrowly scoped worker identity through the supported founder-authorized workflow.
4. Restrict it to the single approved action.
5. Store credentials securely.
6. Bind worker communication to the intended internal endpoint.
7. Configure concurrency of one.
8. Keep scheduling and agent access disabled.
9. Submit one controlled execution.
10. Verify that founder approval is required where applicable.
11. Verify that execution cannot proceed while the emergency stop is engaged.
12. Obtain the necessary founder authorization to release the stop and execute the approved operation.
13. Execute exactly one supervised operation.
14. Verify result integrity and complete audit history.
15. Re-engage the emergency stop.
16. Disable the action.
17. Stop the worker.
18. Revoke temporary credentials where appropriate.

Do not impersonate a founder or create approval records directly in the database.
If interactive founder authentication is unavailable, complete the full sequence in an isolated environment and prepare the minimum necessary founder actions for production.
