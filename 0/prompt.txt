B2.1 — ADVANCED PARTNER PIPELINE
The current platform supports prospect registration and core opportunity tracking.
B2.1 must turn this into a professional, intuitive pipeline.
Partner pipeline
Provide a visual sales pipeline based on the existing authoritative opportunity lifecycle.
Partners should be able to understand:

* Which prospects are active.
* Which require action.
* Which are awaiting founder review.
* Which meetings are pending.
* Which meetings are confirmed.
* Which opportunities are progressing.
* Which opportunities are closed or no longer viable.
* Which require further information.

Do not invent status transitions that conflict with the existing financial or ownership rules.
Views
Implement:

* Kanban-style pipeline where appropriate.
* Table view.
* Compact mobile list.
* Prospect detail.
* Search.
* Filtering.
* Sorting.

Suggested filters:

* Status.
* Assigned partner.
* Service interest.
* Last activity.
* Next action.
* Meeting status.
* Date added.

Partner access must remain limited to their own authorised opportunities.
Founder access must follow the established scope and role controls.
Pipeline interactions
Where supported by the existing state machine:

* Open an opportunity.
* Update permitted information.
* Record an interaction.
* Schedule an internal follow-up.
* Request founder assistance.
* View related meetings.
* Access contextual guidance.
* Review the opportunity's current status.

Do not allow unrestricted drag-and-drop status changes.
Any visual stage transition must call the server's authorised state transition.
If a transition is forbidden, display why.
Never let a UI gesture bypass commission eligibility or ownership checks.
Activity timeline
Create a meaningful, audit-backed timeline.
Potential entries:

* Prospect submitted.
* Founder reviewed.
* Information requested.
* Meeting requested.
* Meeting confirmed.
* Proposal prepared.
* Proposal issued.
* Contract accepted.
* Payment verified.
* Commission event recorded.

Only show events that genuinely occurred.
Do not fabricate activity to populate the interface.
Respect privacy and access restrictions.
B2.2 — INTELLIGENT PROSPECT QUALIFICATION
Build structured, deterministic qualification tools that help partners understand the needs of a business.
Do not start with an expensive AI dependency.
Qualification workspace
Support existing or approved fields such as:

* Business type.
* Location.
* Website availability.
* Current digital presence.
* Services required.
* Main business problem.
* Current supplier.
* Budget indication, where voluntarily provided.
* Desired timescale.
* Decision-maker involvement.
* Existing technical requirements.
* Additional notes.

* Missing discovery information.
* Suggested follow-up questions.
* Related approved Knowledge Base articles.
* Related objection responses.
* Relevant professional resources.
* Technical escalation suggestions.

Use a rules-based model.
Examples:

* Clearly identified business requirement.
* Decision-maker confirmed.
* Relevant service fit.
* Requirements sufficiently documented.
* Timeline understood.
* Scope ready for founder review.

Do not imply a business is guaranteed to purchase.
Do not use protected personal characteristics.
Do not automatically reject a prospect solely because of a score.
Founders must be able to inspect the factors.
Do not let the score override ownership, approval or financial rules.
Duplicate prevention
Review the existing prospect-ownership rules.
Improve duplicate detection where necessary.
Handle:

* Same company with different spelling.
* Duplicate domains.
* Duplicate submissions.
* Concurrent registrations.
* Existing active ownership claims.

Use server-enforced constraints and review processes.
Do not expose another partner's confidential prospect records.
