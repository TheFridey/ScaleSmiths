# Agent discovery metadata

Status: current  
Applies to: the public `web` application

## Principle

Only publish metadata that describes a capability this site genuinely has.

Advertising an endpoint, authentication scheme or payment rail that does not exist is
worse than publishing nothing. An agent that trusts the metadata will fail in a way it
cannot diagnose, retry against a dead endpoint, or attempt a payment that can never
settle. Discovery documents are a promise, not a checklist score.

## Implemented

| Mechanism | Location | Notes |
| --- | --- | --- |
| Link headers (RFC 8288) | `web/next.config.mjs`, served on `/` and `/api/*` | `api-catalog`, `service-desc`, `status`, `sitemap`, `describedby`, `canonical`. Only IANA-registered relations. |
| API catalog (RFC 9727) | `/.well-known/api-catalog` | RFC 9264 linkset, `application/linkset+json`. |
| OpenAPI description | `/openapi.json` | OpenAPI 3.1 for the genuinely public endpoints only. |
| Entity description | `/llms.txt`, `/ai.txt` | Pre-existing. Referenced from the Link header as `describedby`. |
| Sitemap and robots | `/sitemap.xml`, `/robots.txt` | Pre-existing, generated by `app/sitemap.ts` and `app/robots.ts`. |

The Link header value is duplicated between `web/src/lib/agent-discovery.ts` and
`web/next.config.mjs`, because a Next config cannot use the TypeScript path alias.
`agent-discovery.test.ts` fails if the two drift apart.

The OpenAPI document covers `POST /api/quote` and `GET /api/health` only. The admin and
Forge applications are private, are not publicly registrable, and are deliberately not
described. A test asserts that no `/api/forge`, `/api/admin`, `oauth` or `openid` string
ever appears in the published document.

## Deliberately not implemented

These were requested from an external "agent readiness" audit. Each would require
asserting something untrue about this site, or is not a repository artifact. They should
be implemented only after the underlying capability exists.

| Mechanism | Why not |
| --- | --- |
| `/.well-known/openid-configuration`, `/.well-known/oauth-authorization-server` | This site is not an OAuth authorization server. Admin authentication is Auth.js credentials on a separate private application with no public registration, no `authorization_endpoint`, no `token_endpoint` and no `jwks_uri`. Publishing these would advertise an auth flow no agent can complete. |
| `/.well-known/oauth-protected-resource` | There is no publicly reachable protected resource that accepts bearer tokens. `POST /api/quote` is deliberately unauthenticated and rate limited. |
| `/auth.md` | Describes agent registration. There is no agent registration, no credential issuance and no revocation endpoint to describe. |
| `/.well-known/mcp/server-card.json` (SEP-1649) | There is no MCP server. The card's required `transport` endpoint would have to point at something that does not exist. The schema is also still an open pull request against the MCP spec. |
| `/.well-known/agent-skills/index.json` | The RFC requires each entry to carry a resolvable `url` and a `sha256` digest of a real skill document. No skills are published, so the index would be empty or fabricated. Worth adding if and when skills are authored. |
| WebMCP (`navigator.modelContext.provideContext()`) | Technically implementable, but it is a behavioural surface, not metadata: each tool needs a real `execute` path, an input schema and a security review of what an agent may trigger unattended. The only meaningful action here is quote submission, which is already a rate-limited public endpoint described in OpenAPI. Should be scoped as its own change with abuse review. |
| x402, MPP, UCP, ACP | All four are payment and commerce protocols. This site sells nothing over HTTP: there is no wallet address, no facilitator, no priced API operation and no checkout. Adding payment middleware would return `402` with requirements that cannot be settled, and `x-payment-info` on `/openapi.json` would declare charges that do not exist. These belong to a commerce capability that has not been built or decided on. |
| DNS for AI Discovery (DNS-AID) | SVCB/HTTPS records under `_agents.<domain>` plus a DNSSEC-signed zone. This is registrar and DNS-zone configuration, not a repository artifact, and it requires a deployment decision. Documented here so it is not lost. |

## If these are wanted later

The order that keeps the metadata honest:

1. Build the capability (MCP server, OAuth issuer, priced API, published skills).
2. Add its discovery document describing what was actually built.
3. Add a test asserting the document matches the implementation, in the style of
   `agent-discovery.test.ts`.
4. Only then advertise it from the Link header and the API catalog.
